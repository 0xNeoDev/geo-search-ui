Gaia Search Scoring — Final Score Composition

How OpenSearch BM25 text relevance and scoring-service field boosts combine to produce the final ranking. OpenSearch 2.17.1 with default BM25 (k1=1.2, b=0.75).

With text query (boost_mode: "sum") Final = BM25_TextMatch + (max(score_field, -10) + 10) × 1.3
Empty query (boost_mode: "replace") Final = (max(score_field, -10) + 10) × 1.3

What Are the Score Fields?

Three score fields are computed by the scoring-service (Python cronjob) from onchain vote data, then published to Kafka and written to OpenSearch by the search-indexer. The OpenSearch query layer then applies clamping, shifting, and a 1.3× multiplier inside a script_score function before adding it to the BM25 text relevance score.

entity_global_score z-score

What it measures: How popular/reputable an entity is across all spaces.

How it's computed: Raw score = sum of all perspective scores (weighted upvotes − weighted downvotes) across every space the entity appears in. Then z-score normalized: (raw − mean) / stddev across all entities.

Typical: -3 to +3  |  Clamped at: -10

Used by scope: GLOBAL
A z=+3 entity is 3 standard deviations more popular than average.

space_score decay

What it measures: How "close to root" a space is in the space hierarchy.

How it's computed: 0.8 ^ distance_to_root. Pure exponential decay based on graph distance. Root space = 1.0, one hop = 0.8, two hops = 0.64, etc. Disconnected spaces use depth 11 ≈ 0.086. Not z-score normalized — it's already bounded [0, 1].

Range: 0.086 to 1.0  |  Root: 1.0

Used by scope: GLOBAL_BY_SPACE_SCORE
Ranks entities by the authority of their space, not individual popularity.

entity_space_score weighted

What it measures: How popular an entity is within a specific space.

How it's computed: Per-space perspective score (upvotes − downvotes in that space), z-score normalized within the space, then weighted by the space's own score: z_normalized × space_score.

Typical: -3 to +3  |  Clamped at: -10

Used by scope: SPACE_SINGLE, SPACE
An entity highly voted in a root-level space scores higher than one in a distant subspace.

Scoring Pipeline:
Onchain votes → scoring-service raw_score = Σ(upvotes - downvotes) → z-score normalize (raw - μ) / σ → Kafka curation.scores → search-indexer → OpenSearch → Query-time: clamp → shift +10 → ×1.3 → add to BM25

Score Boost Contribution — All Three Fields Compared

The additive contribution from script_score alone: (max(score, -10) + 10) × 1.3. For empty queries (boost_mode: "replace"), this IS the entire final score.
The space_score problem: For empty queries, a root-space entity (space_score=1.0) scores 14.3 while a 5-hop-deep entity scores 13.4 — only a 6% difference for 5 levels of hierarchy. Compare to entity_global_score where a z=+3 entity scores 16.9 vs z=-3 at 9.1 — an 86% difference. Space score has very low discriminating power through the boost formula.

These are additive — a query matching multiple strategies sums their contributions.
Why name matches dominate: BM25 field-length normalization penalizes long fields. A 3-token name gets much higher per-token BM25 than a 20-token description. Combined with the 2.0× name prefix boost, an exact name prefix can outscore a description match by 4-6×. The 0.6× fuzzy penalty ensures typo-tolerant matches rank below exact matches.
